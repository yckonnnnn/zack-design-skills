# 提示词配方

复制粘贴就能用。每条都写明了它触发哪个技能、以及**为什么要这么问**。

设计技能最容易被浪费的方式是「帮我设计好看一点」——这句话没有可执行的含义，模型只会回到默认解。下面这些配方的共同点是：**把要求变成可以检查的条件**。

---

## 一、诊断类

### 1.1 快速体检

```
用 zack-anti-ai-look 的 60 条清单扫一遍这个项目。
先只出诊断表：位置（文件:行）、问题、依据哪一条、严重度。
这个阶段不要改任何代码。
```

> 为什么要分阶段：先改再解释，等于让用户猜你的依据。诊断表本身就是交付物。

### 1.2 只看首屏

```
只看首屏。告诉我：
1. 首屏第一句话能不能让人知道这是干嘛的、给谁用
2. 标题在 1440px 下占几行
3. 主 CTA 点下去会发生什么（能不能从文案看出来）
不要给建议，只回答这三个问题。
```

> 限制输出范围，才能得到真话，而不是一篇客气话。

### 1.3 只读评审（不改代码）

```
用 zack-redesign-audit 的只读评审模式看这个页面。
结论先行：通过 / 有问题 / 未通过，然后给证据表。
按 ROI 排序只给前 10 条建议，其余归入「次要」。
明确写出哪些宽度你没看过。
```

## 二、新建类

### 2.1 先选形式，再写代码

```
用 zack-design-router 判断任务类型，然后帮我做这个 <产品> 的官网。
不要直接写代码。先按 zack-hero-and-pricing 给我首屏的 3 个形式方案，
每个说清：适合什么情况、长什么样、为什么可能不适合我。
我选一个你再写。
```

> 这是整套东西里最有价值的一条。**逼模型先做选择**，是摆脱默认解的唯一办法。

### 2.2 建系统，再铺页面

```
先不要写页面。按 zack-typography-and-color 和 zack-layout-and-rhythm：
1. 给我一张比例字号阶梯表（写清用的比率）
2. 给我 6 级中性色阶的 OKLCH 值，色相按 <品牌色> 偏几度
3. 给我一套间距尺度
4. 给我 1 个强调色，并说明它只出现在哪几个位置
输出成一份 tokens.css。我确认后你再写页面。
```

> 先定表后铺页面，页面才不会「平」。跳过这一步直接写页面，是「每屏都一样」的根因。

### 2.3 指定版式形式

```
这个页面需要 8 个 section。
按 zack-layout-and-rhythm 的版式形式库，选 4 种不同的形式，
每个 section 说明用哪一种、为什么。
禁止：眉标 + 标题 + 副标题 + 三卡 这个组合出现超过一次。
```

> 直接禁用最典型的 AI 版式，比要求「多样一点」有效得多。

### 2.4 定价页

```
按 zack-hero-and-pricing 第二节做价格页。
三档，中间档视觉最重，每档必须写清「不包含什么」。
价格数字用 tabular-nums，三档价格纵向对齐。
给一张真实的功能对比表，不要只有 ✓/✗。
FAQ 4–6 条，每条答案不超过 3 句，必须真的回答问题。
```

## 三、改版类

### 3.1 定范围（必做）

```
用 zack-redesign-audit。动手前先告诉我：
1. 你打算改哪几个文件 / 哪几屏
2. 你确定不改什么
3. 你假设的成功标准是什么
我确认之后你再动手。
```

> 改版最大的成本不是改错，是改了没让改的地方。

### 3.2 零成本高收益优先

```
不要动结构。只做这三件事，然后停下来给我看：
1. 首屏文案改成具体的（保留我的业务事实，不要编数字）
2. 删掉所有渐变、重阴影、emoji 图标、FEATURE 01 这类元标签
3. 收窄首屏标题容器到 2 行以内
一次只改一个主题，每改完一个跑一次构建。
```

### 3.3 建立改动清单

```
改完之后给我一张表：文件:行 / 改前 / 改后 / 依据哪条规则。
然后单独一节列出：你没改的、你没验证的、需要我决定的事。
不要写「提升了整体视觉体验」这类话。
```

## 四、Figma 还原类

### 4.1 标准流程

```
用 zack-figma-to-code 实现这个 Figma 链接的节点。
顺序：get_design_context → get_variable_defs → get_screenshot → 写代码。
先取设计变量，映射到我们现有的 tokens.css，映射表先给我看。
输出必须是我项目的技术栈，不要给我 MCP 默认的 React + Tailwind。
最后给验收报告，包含实际读到的字号、行高、间距、色值。
```

### 4.2 只做验收

```
代码已经写完了。按 zack-figma-to-code 第四节的验收流程，
在 1440 / 1024 / 390 三个宽度下逐项核对，
把差异 > 2px 或色差明显的列出来。先不要改，只出报告。
```

> 「先不要改，只出报告」能避免模型把不对的地方又改错一遍。

## 五、动效类

```
按 zack-motion-taste 处理这个交互。
先回答四个问题：它在解释什么、期间用户能不能操作、出现频率多高、关掉会不会困惑。
答不上来就别做。
如果要做：给出属性、时长（ms）、缓动曲线，并说明退出为什么更快。
最后处理 prefers-reduced-motion 的降级方案。
```

## 六、组合技

### 6.1 一条龙（新建落地页）

```
1. zack-design-router 判定任务类型
2. zack-anti-ai-look 列出这个品类常见的 AI 味陷阱
3. zack-typography-and-color + zack-layout-and-rhythm 建系统（出表，先给我看）
4. zack-hero-and-pricing 做首屏和价格页
5. 其余 section 按版式形式库分配
6. zack-motion-taste 只做必要的动效
7. 三宽度截图自检
每一步做完停下来等我确认。
```

### 6.2 改版一条龙

```
1. zack-redesign-audit 定范围
2. 扫描出技术环境 + 令牌审计（游离色值 / 字号 / 间距各几个）
3. 出诊断表，标 P0/P1/P2，并写出「不建议改的」
4. 按严重度顺序修，一次一个主题
5. 三宽度截图 + 回归清单
6. 交付报告
```

## 七、把要求说死的模板

任何时候不确定怎么提问，套这个句式：

```
【范围】只改 <具体文件/屏>
【依据】按 <技能名> 的 <第几节 / 哪条规则>
【约束】不要 <明确禁止的事>
【验收】做完给我 <具体的证据形式：截图 / 数值表 / 命令输出>
【停手】<在哪一步停下来等我确认>
```

五个空填满，产出质量立刻不一样。**「停手点」是最容易被忽略、也最值钱的一个。**
