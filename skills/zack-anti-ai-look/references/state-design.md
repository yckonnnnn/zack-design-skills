# 状态设计

「补状态」是所有设计建议里最常被说、最少被做完的一条。AI 生成界面时几乎只会画「有数据的正常态」，而真实产品里用户有一半时间不在正常态。

**状态是「有没有想过」的试纸。** 一个把 8 个状态都想过的界面，和一个只有正常态的界面，观感差距比配色大得多。

---

## 一、必须覆盖的 8 个基础状态

| 状态 | 必须包含 | 常见缺失 |
|---|---|---|
| **默认** | 有数据、布局稳定 | — |
| **悬停 hover** | 可交互元素都有反馈 | 只在桌面有意义；触屏要禁用粘滞 hover |
| **聚焦 focus-visible** | 清晰可见的焦点环 | 用 `outline: none` 去掉却不补替代 = 缺陷 |
| **按下 active** | 120ms 内的即时反馈 | 缺了会让界面「像没反应」 |
| **禁用 disabled** | 视觉降级 + 语义禁用 + 不可聚焦 | 只用 `opacity: 0.5` 不够，要 `aria-disabled` |
| **加载 loading** | 骨架屏优于转圈 | 转圈不提供任何信息；超过 300ms 才显示 loading，否则会闪 |
| **空 empty** | 说明为什么空 + 下一步动作 | 「暂无数据」是最偷懒的写法 |
| **错误 error** | 说清发生了什么 + 怎么解决 | 「操作失败」等于没说 |

```html
<!-- 禁用：视觉 + 语义 + 键盘三位一体 -->
<button class="btn" disabled aria-disabled="true">创建密钥</button>

<!-- 焦点：可见且不依赖颜色 -->
<style>
  :focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
</style>
```

## 二、容易被漏掉的进阶状态

这些不在任何基础清单里，但决定产品「像不像做过」。

| 状态 | 什么时候出现 | 设计要点 |
|---|---|---|
| **部分失败** | 批量操作里有些成功有些失败 | 不要整体报错，逐条标出哪几项失败、失败原因、能否重试 |
| **陈旧数据** | 数据过期但还能显示 | 保留数据 + 一行「最后更新于 X 分钟前」+ 刷新按钮。**不要清空** |
| **离线** | 断网 | 明确说是网络问题，不是「出错了」；已缓存内容继续可看 |
| **无权限** | 登录了但没这个权限 | 说清缺什么权限、找谁开通。不要用 404 掩盖 403 |
| **被限流** | 请求过于频繁 | 给出还剩多久可以重试（倒计时），而不是「请稍后再试」 |
| **重试中** | 自动重试 | 显示第几次重试；给用户「立即重试」和「取消」两个出口 |
| **并发冲突** | 两人同时改同一条 | 明确告知冲突在哪几个字段，让用户选择保留哪一版 |
| **超长内容** | 名称、标题过长 | 截断 + `title` / tooltip；表格列用 `max-width` + 省略号 |
| **慢网络** | 3G 级 | 骨架屏形状必须和真实内容一致，否则跳动 |
| **首次使用** | 新用户没有任何数据 | 这是最高价值的空态：引导 + 示例数据 + 一键体验 |

## 三、乐观更新 vs 悲观更新

| | 乐观（先改 UI，再发请求） | 悲观（等成功再改 UI） |
|---|---|---|
| 适合 | 点赞、收藏、切换开关、勾选、本地可撤销的操作 | 支付、删除、发布、任何不可逆或涉及金额的操作 |
| 失败处理 | **必须回滚**，并明确告知失败原因 | 按钮进 loading，成功后再变 |
| 回滚要有动画 | 是。位置直接跳回去比不滚还糟 | — |

**判断标准：操作不可逆吗？涉及钱吗？失败会让用户损失吗？** 任一为是 → 悲观。

## 四、文案写法

| 状态 | 差的写法 | 好的写法 |
|---|---|---|
| 空 | 暂无数据 | 还没有创建密钥。创建第一个密钥，就能开始调用了。 |
| 加载 | 加载中… | （骨架屏，不写文字） |
| 错误 | 操作失败 | 密钥创建失败：名称已被占用。换一个名字再试。 |
| 无权限 | 403 Forbidden | 你需要「管理员」权限才能查看账单。找团队里的 Owner 开通。 |
| 限流 | 请求过于频繁 | 请求太频繁了，28 秒后可以重试。 |
| 离线 | 网络错误 | 网络断了。已加载的内容还能看，恢复后会自动同步。 |

**通用规则**

1. **说清发生了什么**，不要用「出错了」概括。
2. **给出下一步动作**，不要只报告问题。
3. **不要道歉**。「抱歉，出了点问题」不提供任何信息，还显得心虚。
4. **不要用技术术语**。用户不知道什么叫 403、超时、序列化失败。
5. **错误信息不要消失得太快**。toast 至少 5 秒，涉及用户要采取行动的要常驻。

## 五、自检

- [ ] 8 个基础状态都有吗？逐个在代码里搜一遍，不要凭印象
- [ ] `:focus-visible` 有可见样式吗？
- [ ] disabled 是否同时做了视觉、语义和键盘三层？
- [ ] 加载用骨架屏了吗？骨架形状和真实内容一致吗？
- [ ] 空态是否说明了「为什么空」和「下一步做什么」？
- [ ] 错误文案是否说清了原因和解法？
- [ ] 有没有处理部分失败、陈旧数据、离线、限流、无权限？
- [ ] 乐观更新的操作，失败后有没有回滚，回滚有没有告知用户？
- [ ] 触屏上有没有粘滞 hover 的问题？
